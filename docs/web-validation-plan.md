# ShrutDhara — first-release web validation plan

Version 0.1 · 2026-11-21 · Planned checks; none executed by this document

Design: [app design draft 0.4](app-design.md). Behavioral oracle: [use-case specification](use-case-specification.md). The earlier [prototype review](prototype-review.md) tested a different, simulated candidate and cannot supply results for these cases.

## Candidate and matrix

Record app commit/build hash, Angular/worker build IDs, DB/export schema versions, production-like HTTPS origin, content release/recording hashes, codec/bitrate/file sizes/part durations, device model/RAM/Android version, full browser version, install mode, and test time. Local desktop emulation does not qualify as a physical-phone run. Attach actual results and failure evidence to a candidate-bound execution report; a missing device is Blocked, never Passed.

| Candidate environment | Required coverage / support standing |
| --- | --- |
| Owner's primary physical Android phone, Chrome stable at test time | All applicable cases, separately in a normal tab and installed PWA. Fill exact identities before execution. Candidate support target, not a supported-device claim yet. |
| A second physical Android phone with less available memory than the primary | Same audio/offline/restore/update cases in both modes. Record memory and maximum part size; an unspecified emulator or browser resize is not a substitute. Device selection is still pending. |
| Desktop Chrome and Edge stable at test time | Reader, keyboard/focus, backup, range-seeking, storage errors, two-window ownership and update recovery. Desktop success cannot clear the Android listening gate. |
| Other browsers, private mode, iPhone/iPad | No v1 background/PWA support claim. Ordinary page reading may work; feature detection must explain unavailable study persistence/playback features rather than fabricate success. Expand the matrix only through an explicit support decision. |

One supported environment means one exact tested browser/device/mode combination, not all Android phones. Once versions/devices are selected, G-01 records the baseline; P0 results establish whether it is supportable.

## Fixtures and engineering targets

- Use a redistributable real spoken-audio fixture totaling at least thirty minutes, with at least two consecutive parts and known spoken/time markers. Also test the largest encoded part proposed for release. Deliberately short parts used to exercise transitions do not substitute for the long-duration run. If the actual chapter is longer or its largest part is larger, repeat the run with that asset before release.
- A non-scripture spoken fixture is allowed for technical proof and must be labeled. It cannot pass editorial/comprehension checks for the product chapter.
- Prepare one long Hindi reading fixture with stable sutra/block IDs, all three bundled fonts, the largest application font size, a valid backup with distinguishable journeys/bookmarks, malformed/future-version backups, and a revision with intentionally incompatible recording timings.
- Numerical thresholds below are selected engineering targets for the next implementation, not measured results or platform promises. They make failure decidable. Do not weaken them after a failed run without documenting the changed requirement/design standing.

| VP-06 · UC-04 abrupt recovery | During ordinary unsuspended playback, record the media time, abruptly terminate the browser/PWA without orderly pause, then reopen. The actual gesture choice is recorded for G-04; keyboard activation alone does not pass the touch interaction. |
| VP-09 · UC-07, R-07 | Export known separate positions/bookmarks/preferences; alter local state; preview restore, cancel once, then confirm. Try malformed, 5-MiB-limit-plus-one, future-version and missing-content fixtures; abort restore's transaction and fail its pre-restore save. Capture state after pause/drain as the transaction-boundary comparison. | Preview makes replacement explicit. Cancel/invalid/failed transaction applies no imported records. Failed transaction preserves the state at its boundary, including legitimate ordinary checkpoints; do not falsely assert that progress froze while the preview was open. Successful restore restores both journeys/bookmarks/preferences together, remains paused, and preserves unresolved references. Old-epoch callbacks cannot overwrite restored state. Audio is not silently imported/downloaded. Export prepared does not claim successful user retention. |
| VP-10 · UC-09, R-08 | Open a tab and installed window on the same origin. Try simultaneous play/write/restore, handoff, cancel, and leave the owner suspended. Delay/drop handoff messages and inject checkpoint failure. | At most one study owner/player/writer exists. Secondary remains read-only until actual lock acquisition. Ten-second handoff UI timeout gives Retry/Cancel/close-other-window instructions without stealing the lock. Pause/save failure does not release into an unreported lost-state handoff. No nested-lock or coordinator self-wait deadlock. Closing owner allows a new ownership attempt. |
| VP-11 · update/upgrade recovery | Serve build A, begin playback, publish compatible build B in the test environment, leave another controlled window open, select Update later and Prepare update. Inject save failure, then perform close-all/reopen. Repeat while restore is committing and with a blocked DB connection. | No automatic takeover/reload interrupts reading or audio. Update later preserves A. Preparation pauses and commits before safe-close instructions; failed save/Busy offers recovery. Other open windows keep B waiting with explicit instructions. After all controlled clients close, reopen loads compatible B with preserved state, paused. Schema failure retains old records; no destructive fallback. Verify old client asset URLs remain valid on the current test deployment. |
| VP-12 · retention/installation consistency | Pin the playing revision, request removal, cancel once, then Stop and remove. Download a replacement and fail before/after its cache write and metadata commit; retry cleanup. | Active source is never deleted mid-play. Personal positions/bookmarks survive removal; missing revision is visible. Failed replacement keeps old usable media unless the user explicitly chose to remove it first. After successful replacement only current/explicitly retained audio remains, plus justified transient staging. A bookmark alone does not retain old media. Interrupted activation/cleanup reconciles without false readiness. |

VP-01–VP-12 are required before a daily-use release where applicable. Each report records Passed, Failed, Blocked, or Not applicable with a reason. Unavailable controls cannot be marked Not applicable if the release's support declaration promised them; either fix the failure or explicitly revise the support decision.

## Deferred and separate proof

- **Sleep timer experiment:** exercise a five-minute deadline in foreground and with screen locked; record actual audible stop time and lateness. No result is assumed. Do not expose a v1 timer merely because a foreground timeout fires. A later release needs an accepted lateness bound and passing background evidence.
- **Editorial gate:** technical fixtures cannot establish sutra/reference fidelity, rights, translation accuracy, chapter coverage, or pronunciation. UC-01/C-01 require the selected chapter and its actual reviewer/source evidence.
- **Comprehension and usability:** observe intended readers completing reading, listening, resuming and inspecting sources without coaching. Actual product text/audio and sustained font reading are required. Sample screenshots and reflow checks are insufficient.
- **First incompatible correction:** before shipping it, define its real ID/timing mapping or explicit restart flow, preserve the old personal reference, and test both outcomes. General edition-merging machinery is not a v1 prerequisite.

## Recording and release boundary

Keep reproducible scripted fixtures and automated repository/transaction tests with implementation; retain actual physical-device observations separately. Distinguish injected faults from naturally observed device failures. Record raw before/after state, acknowledged checkpoints, revision IDs and actual results without putting private study history into ordinary telemetry. Review failures against the same candidate before expanding scope. This plan creates no test pass, support guarantee, content verification, or deployment authorization.
